# Configuration traceability — 2026-10-04

This inventory covers the 50 buyer areas in the product brief. The audit began October 4; final verification/delivery continued October 5 in Asia/Kolkata. It follows configuration into a runtime consumer and identifies the evidence and limits of each area. The final executed verification results are recorded in [PRODUCT_AUDIT_2026-10-04.md](PRODUCT_AUDIT_2026-10-04.md); historical runs remain in [ATS_ACCEPTANCE.md](ATS_ACCEPTANCE.md).

The shared contract is schemaV2 in `shared/ats-config.cjs`: defaults, migration, field validation, references and module dependencies are checked before generation or activation. Builder writes the validated company configuration into an isolated workspace. Settings saves a draft; review, concurrency checks and activation govern the active configuration in SQLite. Operational records are separate from both source and configuration.

In the table, **API/unit** means executed behavior assertions in the named suites, **browser** means an exercised path in the corporate/agency browser harness, and **source** means a consumer was inspected without claiming complete browser acceptance. These labels describe evidence, not percentages of feature completeness. Backend filenames below live in `server/src/platform/`; frontend consumers live in `src/platform/`. Every generated package uses the same shared validation contract.

## Boundaries that must remain explicit

- Presets are editable starting configurations, not five entirely different products. Campus uses corporate runtime mode; basic uses startup mode. Their own terminology/modules/forms/roles/stage graphs are retained and checked.
- The guided Builder covers normal setup. Advanced automations, organization hierarchies, interview plans, communications, job templates and other schema collections retain general editing surfaces.
- Builder previews are draft renderings with labelled sample records. They use actual careers copy/branding helpers, configured modules, regional formats and workflow/profile labels; they are not an exact rendering of every runtime page or proof of operational writes.
- An explicit empty pipeline graph closes stage moves. A configuration with no graph retains legacy sequential behavior. Changing stage order never silently rewrites edges.
- Public applications require canonical, visible `fullName` and `email` questions; required privacy consent cannot be hidden. The supported transport has one upload question. Invalid configurations fail before activation/generation.
- Top-level `sources`, canonical `documents.categories`, decision reason taxonomies and task choices have operational consumers. Stored tags/skills catalogs, legacy taxonomy sources, custom-domain metadata and provider placeholders must not be marketed as complete functioning capabilities.
- Coverage is broad and representative. It is not an exhaustive action × role × configuration × device matrix, an independent penetration test, native Safari/device certification, or hosted SaaS readiness.
